# Plan T-1.1 — Component registry

## Goal

The component registry exists as pure data: `core` defines the `ComponentKind` / `ComponentCategory` / `ConfigField` / `ComponentDef` types, and `registry` exports a seeded map of all 13 component kinds with the capacity-numbers table from the spec. Nothing renders yet — this is the data layer that the palette (T-1.3), canvas (T-1.2), and simulation (M2) will consume.

**Accept (verbatim from tasks/M1-canvas-and-palette.md):** `ComponentDef` type exactly as in [[02-data-model]]; registry seeded with all 13 kinds and the capacity numbers table; unit test validates every entry (capacity > 0, baseMs > 0, unique kinds).

## Context

Read before coding:

- `../02-data-model.md` — the `ComponentDef` schema (updated 2026-07-12 during planning: `ConfigField` union defined, `category` field added, ∞ = omitted field) and the seed numbers table.
- `../05-engines.md` — engine rules.
- `app/.dependency-cruiser.cjs` — the enforced import rules; `npm run lint` runs depcruise.

Rules that bind this task:

- Engines expose their public API via `index.ts` **only**. `registry` may import `core` only via `../core` (resolves to `core/index.ts` — allowed by the depcruise config).
- No `react` / `next` / `zustand` / `@xyflow` imports anywhere in `src/lib/**`. This task imports nothing at runtime — it is types + data + one lookup function.
- All data must be plain and JSON-serializable: **never use `Infinity`** — unlimited capacity (client, cdn, blob) is an *omitted* capacity field.
- `icon` is a lucide icon name **string**. Do NOT add `lucide-react` (or any dependency) — rendering is a later task's concern.
- Planning decision (already logged in 02-data-model Decisions): types are **defined in `core`**, and `registry/types.ts` re-exports them. This satisfies both the 05-engines table (shared types live in core) and the task's file list.

Current state: `src/lib/core/index.ts` and `src/lib/registry/index.ts` are `export {};` placeholders. `tests/` contains only `smoke.test.ts`. Vitest has no path-alias config, so the test uses a relative import.

### 1. Create `app/src/lib/core/component.ts`

Exact content:

```ts
export type ComponentKind =
  | "client"
  | "lb"
  | "api_gateway"
  | "app_server"
  | "cache"
  | "db_sql"
  | "db_nosql"
  | "queue"
  | "stream"
  | "cdn"
  | "blob"
  | "search"
  | "worker";

export type ComponentCategory =
  | "entry"
  | "network"
  | "compute"
  | "storage"
  | "async";

export type ConfigField =
  | {
      key: string;
      label: string;
      type: "number";
      min: number;
      max: number;
      step: number;
      default: number;
    }
  | { key: string; label: string; type: "boolean"; default: boolean }
  | {
      key: string;
      label: string;
      type: "select";
      options: string[];
      default: string;
    };

export interface ComponentDef {
  kind: ComponentKind;
  label: string;
  category: ComponentCategory;
  /** lucide icon name — rendered by the shell, string only here */
  icon: string;
  /** node accent color, hex */
  color: string;
  /** capacity per instance; an omitted field means unlimited */
  capacity: {
    rps?: number;
    writeRps?: number;
    storageGb?: number;
    connections?: number;
  };
  latency: { baseMs: number };
  consistency: "strong" | "eventual" | "n/a";
  scaling: "horizontal" | "vertical" | "managed";
  configFields: ConfigField[];
}
```

```ts
export const COMPONENT_DEFS: Record<ComponentKind, ComponentDef> = {
  client: {
    kind: "client",
    label: "Client",
    category: "entry",
    icon: "Monitor",
    color: "#64748b",
    capacity: {},
    latency: { baseMs: 1 },
    consistency: "n/a",
    scaling: "managed",
    configFields: [],
  },
  // ... 12 more entries per the tables above
};

export const COMPONENT_KINDS = Object.keys(COMPONENT_DEFS) as ComponentKind[];

export const CATEGORY_ORDER: ComponentCategory[] = [
  "entry",
  "network",
  "compute",
  "storage",
  "async",
];

export function getComponentDef(kind: ComponentKind): ComponentDef {
  return COMPONENT_DEFS[kind];
}
```

### 6. Create `app/tests/registry.test.ts`

Import via the public API with a relative path (no alias configured in vitest):

```ts
import { describe, expect, it } from "vitest";
import {
  CATEGORY_ORDER,
  COMPONENT_DEFS,
  COMPONENT_KINDS,
  getComponentDef,
} from "../src/lib/registry/index";
```

Test cases — implement all of these, exactly this coverage:

1. **all 13 kinds present**: `COMPONENT_KINDS` has length 13 and, sorted, equals `["api_gateway", "app_server", "blob", "cache", "cdn", "client", "db_nosql", "db_sql", "lb", "queue", "search", "stream", "worker"]` (sort the left side in the assertion; uniqueness of kinds follows from this plus the length check).
2. **record keys match entry kinds**: for every `[key, def]` of `Object.entries(COMPONENT_DEFS)`, `def.kind === key`.
3. **every defined capacity number > 0**: for every def, for every value of `Object.values(def.capacity)`, value is a finite number (`Number.isFinite`) and `> 0`. (Also guards against `Infinity` sneaking in.)
4. **baseMs > 0**: for every def, `def.latency.baseMs > 0`.
5. **configFields are well-formed**: for every def — field `key`s unique within the def; every `type: "number"` field has `min < max`, `step > 0`, and `min <= default && default <= max`; every `type: "select"` field's `default` is included in its `options`.
6. **getComponentDef**: `getComponentDef("db_sql")` returns the same object as `COMPONENT_DEFS.db_sql`, and its `capacity.writeRps` is `15000`.
7. **CATEGORY_ORDER covers all categories in use**: every `def.category` is included in `CATEGORY_ORDER`, and `CATEGORY_ORDER` has no duplicates.

Use plain loops + `expect` inside the tests; when asserting per-entry, prefer `expect(x, def.kind).toBe(...)`-style messages or wrap in `for` loops over `Object.values(COMPONENT_DEFS)` so a failure names the offending kind.
