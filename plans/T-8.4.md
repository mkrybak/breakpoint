# T-8.4 — Sequential calls add latency

## Goal

Make the client-path latency fold say what it means. A node's mean path latency is its own latency plus, for each live sync outbound edge, `weight × callee path latency`. Edges are weighted in one of two ways. A **call** (any non-LB source) is a sequential call, so its callees **add up**, each weighted by `callsPerRequest` times the share of the source's traffic that actually leaves it. A cache therefore charges its DB only for misses + writes. A **split** (LB source) is a true flow-weighted **average** over the live backends. Async edges stay off the client path. A dead (partitioned) edge carries no flow and so adds no latency. The fold is split into two exported pieces, `clientPathTerms` (the weights) and `meanPathMs` (the fold), so T-8.7 can swap the `1.6 × mean` tail without touching the weighting.

**Accept (verbatim):** A node's client-path latency = own latency + the **sum** of its sync calls' latencies, weighted by `callsPerRequest`. Today it's a traffic-weighted *average*, which is right only for LB splits, and LB edges keep the average. Golden test: an app calling a cache and then a DB sequentially pays both.

**Key finding (lead, please review).** Today's fold is already a *sum*: `ms += (flow(e) / served(source)) × path(target)`, and it is never normalized. It only behaves like an average because the old sum-to-1 warning pushed users to set 0.5 / 0.5 on fan-outs. Once T-8.3 makes non-LB edges multiply by `callsPerRequest`, `flow(e) / served(source)` equals `callsPerRequest × passThrough(source)` exactly, which is the Accept rule. So for call edges **the formula does not change**. I checked this with the current engine, using trafficShare 1 / 1 as a stand-in for cpr 1 / 1: app → cache + app → db gives p95 37.40 ms, against 32.15 ms for the old 0.5 / 0.5. The real code change is therefore:
1. **LB splits become a normalized average:** `weight = flow(e) / Σ flow over the LB's forward sync edges`. Today's denominator is `served(lb)`, and the two differ only when an LB edge is dead (partition) or the LB's shares don't sum to 1. With 2 backends at 0.5 / 0.5 and one partitioned, today's p95 *drops* to 11.77 ms (half the live backend's latency, so a partition flatters the design). After the change it is 20.30 ms (the live backend in full). The stranded half is still reported as errors through `unroutable`. **This is my call.** It is the literal "flow-weighted average", and it is in M8's spirit of not flattering wrong designs.
2. Separating the weights from the fold, for T-8.7.
3. Golden tests and spec.

How caches fit (the exact rule): a call edge's weight is **flow-derived, never read from `edge.callsPerRequest`**. For a cache, `flow(cache→db) = (read·(1−hitRate) + write) × cpr`, while `served(cache) = read + write`. So the weight is `cpr × (misses + writes) / served`. Golden 2's numbers give 3600 / 10000 = 0.36. The cache's own latency is paid by all traffic reaching it, hits and misses. A flush override (`effects.hitRate`) flows through automatically. Using `edge.callsPerRequest` directly would charge the DB on hits, so it is forbidden.

Other semantics, pinned:
- **Async edges** are skipped (unchanged). **Edges leaving an async-category node (queue/stream) are skipped too.** T-8.2 already made `meanPathMs` stop at async nodes; keep that rule in `clientPathTerms` (the code above does) and keep T-8.2's golden for it green.
- **Dead (partitioned) edges** stay in the term list with flow 0 → weight 0. For a call this is right: the requests that made the call failed (counted in errorRate via `unroutable`), and the survivors never made it. For a split, the 0 flow also drops out of the denominator.
- **Back / self / into-entry edges** are skipped by the same `position` rule as today.
- **`served(source) = 0`** (down node) or an LB denominator of 0 → weight 0, and the path is the node's own latency (unchanged).
- Calls are modelled as **sequential**: three calls to the DB per request (cpr 3) pay the DB path 3×. Parallel fan-out (max instead of sum) is not modelled. This is logged as a Decision.
- **Float order is preserved:** `ms` starts at `out.latencyMs`, then `+=` each term in `graph.edges` order, exactly as today. So every existing `toBe`-exact golden keeps its value.

## Steps

1. **`app/src/lib/simulation/engine.ts`: add `PathTerm` + `clientPathTerms`.** Place them directly above `meanPathMs` and import `isSplitSource` (see the assumption above).

   ```ts
   /** One sync child on a node's client path. */
   export interface PathTerm {
     target: string;
     /**
      * Share of the source's requests that pay the target's path latency.
      * call (non-LB source): flow(e) / served(source) = callsPerRequest ×
      *   pass-through (a cache passes only misses + writes) — calls ADD.
      * split (LB source): flow(e) / Σ flow over its forward sync edges —
      *   backends AVERAGE over live edges.
      */
     weight: number;
   }

   /**
    * Client-path weights per reachable node (tick-loop step 4), separate from
    * the fold so tail models (T-8.7) reuse them. Sync forward edges only, in
    * graph.edges order; dead edges stay with weight 0 (flow 0). Weights are
    * flow-derived, never edge.callsPerRequest, so cache hits never pay the DB.
    */
   export function clientPathTerms(
     graph: DesignGraph,
     prop: PropagationResult,
     outputs: ReadonlyMap<string, NodeModelOutput>,
   ): Map<string, PathTerm[]> {
     const position = new Map(prop.order.map((id, i) => [id, i]));
     const nodeById = new Map(graph.nodes.map((n) => [n.id, n]));
     const terms = new Map<string, PathTerm[]>();
     prop.order.forEach((id, i) => {
       const node = nodeById.get(id);
       const out = outputs.get(id);
       if (!node || !out) return;
       // T-8.2 (lead): consumers pull from a queue/stream, so nothing past an async node is on the client path
       const asyncSource = getComponentDef(node.kind).category === "async";
       const edges = graph.edges.filter((edge) => {
         if (asyncSource || edge.source !== id || edge.kind === "async") return false;
         const to = position.get(edge.target);
         return to !== undefined && to > i;
       });
       const flows = edges.map((edge) => flowRps(prop.perEdge[edge.id]));
       const denominator = isSplitSource(node.kind)
         ? flows.reduce((sum, f) => sum + f, 0)
         : flowRps(out.served);
       terms.set(
         id,
         edges.map((edge, k) => ({
           target: edge.target,
           weight: denominator > 0 ? flows[k] / denominator : 0,
         })),
       );
     });
     return terms;
   }
   ```

2. **Same file: rewrite `meanPathMs` as the fold over the terms and export it.** Replace its doc comment and body:

   ```ts
   /**
    * Mean client-visible latency (tick-loop step 4): reverse topo order,
    * path(n) = latencyMs(n) + Σ weight × path(target) over clientPathTerms.
    * Sequential calls sum; LB splits average; async/dead edges add nothing.
    */
   export function meanPathMs(
     graph: DesignGraph,
     prop: PropagationResult,
     outputs: ReadonlyMap<string, NodeModelOutput>,
   ): number {
     const terms = clientPathTerms(graph, prop, outputs);
     const pathMs = new Map<string, number>();
     for (let i = prop.order.length - 1; i >= 0; i--) {
       const id = prop.order[i];
       const out = outputs.get(id);
       if (!out) continue;
       let ms = out.latencyMs;
       for (const term of terms.get(id) ?? []) {
         ms += term.weight * (pathMs.get(term.target) ?? 0);
       }
       pathMs.set(id, ms);
     }
     return pathMs.get(graph.entryNodeId) ?? 0;
   }
   ```
