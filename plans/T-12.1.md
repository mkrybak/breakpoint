# T-12.1 — Verdict and hint understand breakers

## Goal

When a run fails on errors and an open circuit breaker caused some of those errors by failing calls fast, the verdict says so. It names the breaker's target, says how many requests it failed fast, and says whether the breaker closed again for good. The Quick challenge card's "Not yet" hint then points at capacity behind the breaker instead of the static hint ("add a replica" to the app server, which the user may already have done). The facts are folded from frames. The only engine change is one optional reporting field on `EdgeFrame`; simulation behaviour does not change.

**Accept (verbatim):** When a run fails on errors and some of those errors were fail-fast rejections by an open breaker, the verdict says so: which breaker, how many requests it failed fast, and whether its target recovered (e.g. "Your breaker protected Payments API (recovered at 21 s), but 9k requests failed fast while it was open. Add capacity so it doesn't trip."). The challenge nudge stops suggesting a fix the user already made, and points at capacity behind the breaker instead. The verdict facts come from frames; no new engine behaviour.

Calls made (lead: please review):
1. **One optional frame field is needed.** The frames can't tell us how much a breaker failed fast. While the breaker is open, `perEdge.rps` is 0 and the rejected flow sits inside `perNode[source].dropped`, mixed with the source's own drops and any partitioned edges. So `EdgeFrame` gains `failedFastRps?: number`. It is present only on breaker edges, and only on ticks where the breaker rejected calls (open or half-open). This is reporting only: no numbers or events change. The lead allowed this ("optional frame fields if truly needed"). It touches `engine.ts` and `core/sim-result.ts`, which aren't in the task's Files list. T-12.2 and T-12.5 edit `engine.ts` too, in different spots (events and tail contribution).
2. **The facts are a structured optional field on `Verdict`,** `breakerTrips?: BreakerTrip[]`, not advisory strings. Two reasons: the full Verdict shows advisories only on a pass and the plain variant drops them, and the nudge needs the target label. The field is present only when non-empty, so existing `toEqual` verdict tests and persisted or imported runs stay valid.
3. **"Recovered at"** is the `t` of the first frame in the run's final unbroken stretch of `breaker: "closed"` frames. That is the first tick after the last successful probe, so a breaker that closes and then re-opens doesn't count as recovered. If the last frame is not closed, it is `null` ("still open when the run ended").
4. **"Requests failed fast"** is Σ `failedFastRps` ÷ 10 over the run: the calls rejected on that edge, including half-open's 90% and any rejected retries. This equals requests when `callsPerRequest` is 1. Only breakers whose source is reachable from the entry over sync edges count (`syncReachability`), because a worker's breaker behind a queue doesn't feed `errorRate`.
5. **Gating is in the shell.** Breaker lines show only when `!passed`, at least one failure is `error-rate` or `kill-survival`, and trips exist. When breaker lines show, the plain verdict drops the generic `PLAIN_CAPACITY_TIP`, because the breaker line already names the node and the fix. The copy uses `formatSec` ("21.4s"), the same as the neighbouring plain lines.
6. **The copy helpers live in `hud-format.ts`,** next to `describeVerdictPlainly`, and the nudge hint lives in `challenge-nudge.ts`. `ChallengeCard.tsx` changes by one expression. Neither file is in the Files list. Both are needed. The grader markdown report (`persistence/report.ts`) is not changed (possible follow-up).
7. The event log is untouched (T-12.2 owns it).

Measured: `examples/retry-storm.json` with the default breaker on `e-app-dep` × `quick-spike-3x`. The breaker opens at 10.6 s, re-opens at 16.3 s, and is closed from 21.4 s to the end. App fleet drops 43,986 requests during non-closed ticks. App fleet is never overloaded, so that number is exactly the fail-fast total. Expected plain line: "Your breaker protected Dependency (recovered at 21.4s), but 44k requests failed fast while it was open. Add capacity to Dependency so it doesn't trip." The same design × `black-friday` ends with the breaker open, so it shows the "still open" copy.

3. **`app/src/lib/simulation/verdict.ts`**: add `BreakerTrip` to the core type import, and add this above `criteria`:
   ```ts
   /** Breakers on the client's sync path that failed calls fast (T-12.1), most failed-fast first. */
   export function collectBreakerTrips(
     graph: DesignGraph,
     frames: SimFrame[],
   ): BreakerTrip[] {
     if (frames.length === 0) return [];
     const reached = syncReachability(graph);
     const labelById = new Map(graph.nodes.map((n) => [n.id, n.label]));
     const trips: BreakerTrip[] = [];
     for (const edge of graph.edges) {
       if (!reached.has(edge.source)) continue;
       let failedRps = 0;
       for (const f of frames) failedRps += f.perEdge[edge.id]?.failedFastRps ?? 0;
       const failedFast = failedRps / TICKS_PER_SEC;
       if (failedFast < 1) continue;
       const phase = (i: number) => frames[i].perEdge[edge.id]?.breaker;
       let recoveredAtSec: number | null = null;
       if (phase(frames.length - 1) === "closed") {
         let k = frames.length - 1;
         while (k > 0 && phase(k - 1) === "closed") k--;
         recoveredAtSec = frames[k].t;
       }
       trips.push({
         edgeId: edge.id,
         sourceLabel: labelById.get(edge.source) ?? edge.source,
         targetId: edge.target,
         targetLabel: labelById.get(edge.target) ?? edge.target,
         failedFast,
         recoveredAtSec,
       });
     }
     return trips.sort((a, b) => b.failedFast - a.failedFast);
   }
   ```

   /** Request count → "950", "9k", "12.3k" (k-suffix at/above 1000, no trailing ".0"). */
   export function formatCount(n: number): string {
     return n >= 1000 ? `${Number((n / 1000).toFixed(1))}k` : `${Math.round(n)}`;
   }

   const ERROR_CRITERIA = new Set(["error-rate", "kill-survival"]);

   /** Breaker trips worth explaining: the run failed on errors and a breaker failed calls fast. */
   export function breakerTripsBehindErrors(verdict: Verdict): BreakerTrip[] {
     if (verdict.passed) return [];
     if (!verdict.failures.some((f) => ERROR_CRITERIA.has(f.criterion))) return [];
     return Array.isArray(verdict.breakerTrips) ? verdict.breakerTrips : [];
   }

   /** One sentence crediting the breaker and naming the remaining fix. */
   export function describeBreakerTrip(trip: BreakerTrip): string {
     const n = formatCount(trip.failedFast);
     const fix = `Add capacity to ${trip.targetLabel} so it doesn't trip.`;
     return trip.recoveredAtSec === null
       ? `Your breaker protected ${trip.targetLabel}, but it was still open when the run ended: ${n} requests failed fast. ${fix}`
       : `Your breaker protected ${trip.targetLabel} (recovered at ${formatSec(trip.recoveredAtSec)}), but ${n} requests failed fast while it was open. ${fix}`;
   }
