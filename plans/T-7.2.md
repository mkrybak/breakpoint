# T-7.2 — Mode on the design record

## Goal

Make the product mode a piece of data on every saved/exported design so the shell (landing page, `/design/[id]`) can branch on it. `DesignRecord` gains a required `mode` field typed `"quick" | "practice" | "interview"`. Old records and imported files without it (or with a bad value) parse as `"practice"`, with no migration. `buildDesignRecord` takes the mode as a required argument, so every call site has to state it. The design store holds the attached design's mode, autosaves it, and keeps it when the user imports a file in place. Engines stay unaware of modes.

Accept (verbatim from `tasks/M7-quick-mode.md`):

> `DesignRecord.mode: "quick" | "practice" | "interview"`. Records and imports without the field load as `"practice"` (no migration). `buildDesignRecord` takes the mode. Export round-trips it. Engines (`src/lib/**`) stay mode-unaware.

Binding spec rule (product-modes design, "How it's built"): **importing never converts a mode.** The workspace's in-place "Import JSON" keeps the current design's mode and ignores the file's. Importing as a *new* design (landing page, review-screen bundle import) uses the file's mode, or `"practice"` if it's missing.

Engine rules: `DesignMode` is a **shell** type. It lives in `src/persistence/local.ts`, not in `src/lib/core`. Nothing under `src/lib/**` changes. No new imports into engines and no new dependencies.

Calls made in this plan (for the lead to review):
1. **`mode` is a required positional parameter right after `graph`**: `buildDesignRecord(id, name, graph, mode, phaseNotes?, actionLog?)`. A defaulted/optional `mode` would let the autosave or export silently write `"practice"` over a Quick design. If the parameter is required, `tsc` flags every call site. Existing calls that pass `phaseNotes` in 4th position also fail typecheck (a `Record` is not a `DesignMode`), so none are missed.
2. **Invalid mode values parse as `"practice"`**, the same as a missing field. This follows the "forgiving on the rest" policy of `parseDesignRecord`; only the graph is strict. `"interview"` is a valid value and is preserved. Opening it in the Practice layout with a notice is T-7.5's job.
3. **The store exposes `designMode: DesignMode`**, defaulting to `"practice"`. `attachDesign` sets it to `record?.mode ?? "practice"`. `importRecord` never touches it, which implements the in-place rule. The value is only meaningful once `designId` equals the page's id. Before the first attach it reads `"practice"`, and T-7.5 should gate on `designId === id` so it doesn't flash the Practice layout.
4. **Import as a new design needs no helper.** The landing page has no design-file import today, and T-7.4's Accept doesn't add one. `parseDesignRecord` already yields "file's mode or practice". If a landing import is ever built, it does `saveDesign({ ...parsed, id: crypto.randomUUID() })`. The review screen's `ImportDropzone` already saves `bundle.design` verbatim, so it keeps the bundle's parsed mode. It needs no change.
5. The autosave equality check does **not** add `designMode`. Mode only changes through `attachDesign`, and the subscription already skips designId changes. When the same id is re-attached, the graph also changes, and the save writes the correct mode.
6. T-7.1's e2e seeds `bp:design:e2e-twitter` without `mode`. That record now parses as `"practice"`, so it opens in the Practice layout, which is exactly what the smoke test expects. No conflict.

Deviations from the task's Files list: `tests/design-store.test.ts` gets the store tests, and `tests/actions-store.test.ts` and the three components get mechanical call-site updates. `02-data-model.md` gets the `mode` field plus a Decisions line, per sdlc "update the note in the same session".

- Creating a Quick design (T-7.4): `saveDesign(buildDesignRecord(id, name, starterGraph, "quick"))`. A new Practice design (T-7.4/T-7.7): `buildDesignRecord(id, name, emptyGraph, "practice")`.
