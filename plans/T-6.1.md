# T-6.1 — Auto-balancing load balancer

## Goal

**Accept (verbatim):** Wiring an `lb` node to N backends auto-assigns each outbound edge an even `1/N` share (no manual entry, no sum-to-1 warning). Shares recompute when a backend is added or removed, on edits only — never on graph load/import. A share can still be overridden by hand: typing a value or unchecking "Auto" flips that edge to a fixed slice while the remaining auto edges divide what's left; a manual edge offers a reset back to auto. The simulation engine and validation logic are unchanged (`trafficShare` stays a materialized number). Only `lb`-source edges are affected; all other fan-out nodes keep manual shares. `local.ts` import accepts an optional `autoShare` boolean with no migration.

When done: connecting an LB to backends on the canvas shows edge labels like `50% · auto`; the selected-edge inspector for LB-source edges gains an "Auto" checkbox (checked by default) next to the share input; typing a share or unchecking Auto pins that edge and the remaining auto edges split the remainder; re-checking Auto hands the edge back to the even split. Everything else on the canvas, in the engine, and in validation behaves exactly as today.

Design source of truth: `docs/superpowers/specs/2026-07-19-auto-balancing-lb-design.md` (approved). This plan implements it against current code.

## Reality vs. spec (read this first)

- **Node deletion does NOT cascade edge removals through `onEdgesChange`.** The spec asked to confirm this during planning; confirmed: dangling edges are dropped by `fromFlow`'s `nodeIds.has(...)` filter *inside* `onNodesChange` (proved by the existing design-store test "cascades delete to dangling edges", which calls only `onNodesChange`). So `onNodesChange` **must** rebalance LBs that lost a backend (step 3d). When React Flow's UI delete path *also* emits edge `remove` changes via `onEdgesChange`, the rebalance runs twice — it is idempotent, so that's harmless.
- **`rebalanceLb` checks the node kind itself** (`kind !== "lb"` → returns the graph unchanged). Call sites can then call it unconditionally after any mutation, which keeps `onConnect`/`updateEdge` free of duplicated lb checks.
- **An auto LB edge's `trafficShare` is always store-owned.** After this change, `updateEdge(id, { trafficShare })` alone on an auto LB edge gets immediately recomputed by the rebalance — by design. The UI therefore always sends `{ autoShare: false, trafficShare }` when the user types (spec's rule). The existing test "updateEdge patches trafficShare and kind" targets `e-lb-app` (an LB edge, auto-by-absence) and must be updated to pass `autoShare: false` (step 6b).
- **Source kind is threaded through `flow-adapter`**, not looked up in the store from `FlowEdge` (the spec allowed either). `FlowEdgeData` gains an optional `sourceKind` — keeps `FlowEdge` a pure render of its `data` and testable via the adapter tests. The existing flow-adapter assertion `expect(edges[0].data).toEqual({ trafficShare: 1, kind: "sync" })` gains `sourceKind: "client"` (step 6a).
- **UI consolidation:** the spec sketches a checked "Auto" checkbox for the auto state and a separate "↺ auto" control for the manual state. One persistent "Auto" checkbox covers both with the exact same `updateEdge` calls the spec names (unchecking → `{ autoShare: false, trafficShare: current }`; re-checking → `{ autoShare: true }` = the reset). One control, no duplicate affordance.
- **Deviation note to record after implementing** (tick the T-6.1 checkbox in `tasks/M6-post-mvp-features.md` and add a one-liner under the task): tests (`design-store`, `flow-adapter`, `persistence`) and the `02-data-model.md` doc touch-up are edited beyond the task's Files list; no engine file changed.

### 3. `src/stores/design-store.ts` — `rebalanceLb` + the four triggers

**3a. Helper.** Add after the `emptyGraph()` function, exported for tests:

```ts
/**
 * T-6.1: recompute one LB's auto outbound shares — auto edges (autoShare !==
 * false) evenly divide max(0, 1 − Σ manual shares). No-op for non-lb sources
 * and for LBs with no auto edges, so call sites invoke it unconditionally.
 * Never called from attachDesign/importRecord/setGraph: loads and imports keep
 * their stored shares until the next edit.
 */
export function rebalanceLb(graph: DesignGraph, sourceNodeId: string): DesignGraph {
  const node = graph.nodes.find((n) => n.id === sourceNodeId);
  if (node?.kind !== "lb") return graph;
  const outbound = graph.edges.filter((e) => e.source === sourceNodeId);
  const autoCount = outbound.filter((e) => e.autoShare !== false).length;
  if (autoCount === 0) return graph;
  const manualSum = outbound
    .filter((e) => e.autoShare === false)
    .reduce((acc, e) => acc + e.trafficShare, 0);
  const share = Math.max(0, 1 - manualSum) / autoCount;
  return {
    ...graph,
    edges: graph.edges.map((e) =>
      e.source === sourceNodeId && e.autoShare !== false
        ? { ...e, trafficShare: share }
        : e,
    ),
  };
}
```

**3d. `onNodesChange`.** Replace the whole implementation — node deletion cascades dangling edges inside `fromFlow` (see Reality vs. spec), so LBs that just lost a backend rebalance here:

```ts
  onNodesChange: (changes) =>
    set((s) => {
      const { nodes, edges } = toFlow(
        s.graph,
        s.selectedNodeIds,
        s.measured,
        s.selectedEdgeIds,
      );
      const nextNodes = applyNodeChanges(changes, nodes);
      let graph = fromFlow(nextNodes, edges, s.graph.entryNodeId);
      // fromFlow drops edges whose endpoint was removed (no onEdgesChange
      // round-trip), so LBs that lost a backend must rebalance here (T-6.1).
      const removedIds = new Set(
        changes.filter((c) => c.type === "remove").map((c) => c.id),
      );
      if (removedIds.size > 0) {
        const affectedSources = new Set(
          s.graph.edges
            .filter((e) => removedIds.has(e.target) && !removedIds.has(e.source))
            .map((e) => e.source),
        );
        for (const src of affectedSources) graph = rebalanceLb(graph, src);
      }
      return {
        graph,
        selectedNodeIds: nextNodes.filter((n) => n.selected).map((n) => n.id),
        measured: collectMeasurements(nextNodes),
      };
    }),
```
