# T-13.5 — API board

## Goal

The API step gets its own board in the center slot that T-13.2 creates. It is a vertical list of endpoint cards with "+ Endpoint" at the top. Each card has a method picker colored per method, a monospace URL, a status code, and request and response JSON bodies side by side. The bodies get light, dependency-free syntax coloring (a highlighted `<pre>` under a transparent `<textarea>`). Invalid JSON gets a subtle "not valid JSON" hint and is stored exactly as typed. While the API step is viewed, the right column shows a read-only list of the design's entity names. The board takes a `readOnly` prop so T-13.6 can reuse it on the review screen.

**Accept (verbatim):**
- A vertical list of endpoint cards with "+ Endpoint" at the top.
- Each card has a method picker (GET/POST/PUT/PATCH/DELETE, colored per method), a monospace URL field, a status code field, and request and response JSON text areas side by side with light syntax coloring.
- Invalid JSON gets a subtle "not valid JSON" hint and is stored exactly as typed. It never blocks typing, saving or export (review focus 4: a unit test that round-trips half-typed JSON through record and bundle).
- Cards can be deleted and reordered.
- The workspace's right column shows a read-only list of the design's entity names while on the API step.
- Screenshots: two endpoints, one with invalid JSON.

## Context

**Rules:** this is shell-only work, and nothing in `src/lib/**` changes. The pure helpers go in a `.ts` file under `components/boards/api/`. They take strings and return plain data, so vitest (node env, `.test.ts` only) can test them without a DOM. No new dependency: the icons come from `lucide-react`.

**Calls made here (lead, review):**
- **Coloring approach:** a `relative` wrapper holds an in-flow `<pre aria-hidden>` with colored `<span>`s, which sets the height. Over it sits an `absolute inset-0` `<textarea>` with transparent text and a visible caret. Both use identical font, padding, `whitespace-pre-wrap` and `wrap-break-word`, so the glyphs line up. The field grows with its content, so there's no inner scroll to keep in sync. The tokenizer is one sticky regex and is **lossless**: the token texts concatenate back to the input exactly, for any input. This was fuzz-checked on 20k random strings over a JSON-ish alphabet. An unterminated string stops at the end of the line, so a half-typed `"` doesn't color the rest of the body.
- **Validity:** a body that is empty or only whitespace gets no hint (GET has no body). Otherwise `JSON.parse` decides. The hint row always reserves its 16 px, so the card doesn't jump while typing. No debounce: the hint follows each keystroke, which is the cheapest option and is never blocking.
- **Reorder** uses ↑/↓ icon buttons per card (keyboard-accessible by default) instead of drag-and-drop. Cards are tall, which makes dragging clumsy, and the criteria only ask for "reordered". Alt+↑/↓ from any field in the card also moves it, matching T-13.3's requirement items. Focus stays where it was, on the clicked button or in the field.
- **Keyboard flow:** Enter in the URL field moves focus to status. Enter in status moves focus to the request body. Ctrl/⌘+Enter anywhere in a card adds a new endpoint (appended) and focuses its URL. "+ Endpoint" does the same. After a delete, focus goes to "+ Endpoint". There's no confirm dialog, matching node delete. Tab in a body moves focus as usual and doesn't indent (accessibility).
- **Status tint:** 2xx emerald, 3xx sky, 4xx amber, 5xx rose, anything else neutral. The value is only tinted, never validated.
- **Method picker** is a native `<select>`, tinted per method (GET sky, POST emerald, PUT amber, PATCH violet, DELETE rose).
- **`EntityNamesPanel` is mounted via T-13.2's `STEP_ASIDES` map** (`api: EntityNamesPanel`), so it shows only while the viewed step is API. It lists non-blank entity names in board order.
- **`readOnly`** (for T-13.6): the board renders the passed `board` and never touches `useDesignStore`. In read-only mode there's no "+ Endpoint", no move or delete, and no inputs. The method shows as a tinted badge, the URL as `<code>`, and the bodies as the colored `<pre>` alone. An empty body shows a muted "empty", and invalid JSON still gets its hint.
- **Extra e2e** `e2e/api-board.spec.ts`. It's a separate file so it can't collide with T-13.2 and T-13.6 editing `practice-steps.spec.ts`. It proves in a real browser that half-typed JSON survives a reload.

**Expected deviations from the Files list:** `src/components/boards/StepBoard.tsx` (replace the api placeholder, add `api: EntityNamesPanel` to `STEP_ASIDES`), new `tests/api-board.test.ts`, new `e2e/api-board.spec.ts`, and one Decisions line in `tasks/M13-practice-step-boards.md`.

1. **`app/src/components/boards/api/api-format.ts`** (new, pure, no `"use client"`):
   ```ts
   import type { HttpMethod } from "@/lib/core";
   // HTTP_METHODS comes from @/persistence/boards (T-13.1); do not redefine it here.

   /** Tint per method (border + text); key order is the picker order. */
   export const METHOD_STYLES: Record<HttpMethod, string> = {
     GET: "border-sky-500/50 text-sky-300",
     POST: "border-emerald-500/50 text-emerald-300",
     PUT: "border-amber-500/50 text-amber-300",
     PATCH: "border-violet-500/50 text-violet-300",
     DELETE: "border-rose-500/50 text-rose-300",
   };

   /** Text tint for a raw status string by class (2xx…5xx); never validates. */
   export function statusTone(status: string): string {
     const s = status.trim();
     if (/^2\d\d$/.test(s)) return "text-emerald-300";
     if (/^3\d\d$/.test(s)) return "text-sky-300";
     if (/^4\d\d$/.test(s)) return "text-amber-300";
     if (/^5\d\d$/.test(s)) return "text-rose-300";
     return "text-neutral-100";
   }

   export type JsonStatus = "empty" | "valid" | "invalid";
   /** Whitespace-only counts as empty (no hint); otherwise JSON.parse decides. */
   export function jsonStatus(text: string): JsonStatus {
     if (text.trim() === "") return "empty";
     try { JSON.parse(text); return "valid"; } catch { return "invalid"; }
   }

   export type JsonTokenKind = "key" | "string" | "number" | "literal" | "punct" | "text";
   export interface JsonToken { kind: JsonTokenKind; text: string }
   export const TOKEN_CLASS: Record<JsonTokenKind, string> = {
     key: "text-sky-300", string: "text-emerald-300", number: "text-amber-300",
     literal: "text-violet-300", punct: "text-neutral-500", text: "text-neutral-200",
   };
   ```
   Then `tokenizeJson`, verbatim (verified lossless):
   ```ts
   // One sticky scan; every alternative consumes >= 1 char, so the loop ends and
   // the token texts concatenate back to the input exactly (any input, valid or not).
   const TOKEN_RE =
     /("(?:[^"\\\n]|\\.)*"?)(\s*:)?|(-?\d+(?:\.\d+)?(?:[eE][+-]?\d+)?)|(true|false|null)(?![A-Za-z0-9_])|([{}[\],:])|([^"\-\d{}[\],:tfn]+|[\s\S])/y;

   /** Lossless, forgiving JSON tokens for coloring; half-typed input is fine. */
   export function tokenizeJson(text: string): JsonToken[] {
     const tokens: JsonToken[] = [];
     const push = (kind: JsonTokenKind, t: string) => {
       const last = tokens[tokens.length - 1];
       if (last !== undefined && last.kind === "text" && kind === "text") last.text += t;
       else tokens.push({ kind, text: t });
     };
     TOKEN_RE.lastIndex = 0;
     while (TOKEN_RE.lastIndex < text.length) {
       const m = TOKEN_RE.exec(text);
       if (m === null) break;
       if (m[1] !== undefined) {
         if (m[2] !== undefined) {
           push("key", m[1]);
           if (m[2].length > 1) push("text", m[2].slice(0, -1));
           push("punct", ":");
         } else push("string", m[1]);
       } else if (m[3] !== undefined) push("number", m[3]);
       else if (m[4] !== undefined) push("literal", m[4]);
       else if (m[5] !== undefined) push("punct", m[5]);
       else push("text", m[0]);
     }
     return tokens;
   }
   ```
