# T-12.2: Event log tells the truth around breakers

## Goal

The event log stops lying around circuit breakers. Today a node whose load disappears because the breaker in front of it opened logs a green "X recovered". A breaker that closes and then trips again 0.5 s later logs a burst: half-open, closed (green), overloaded, open, recovered (again false). After this task:
- a node that is `ok` only because breakers cut all of its load logs a neutral "X idle (breaker open)";
- "recovered" is logged when it serves real traffic again;
- a breaker that re-opens within 1 s of closing logs one "breaker re-opened 0.5 s after closing" line.

This changes log lines only. Every other frame field is byte-identical (checked with a prototype across all examples and presets).

**Accept:** A node whose load drops because an upstream breaker opened logs "X idle (breaker open)" (neutral), not a green "X recovered". "Recovered" is logged only when the node serves real traffic again. A breaker that re-opens within 1 s of closing logs one line ("breaker re-opened 0.5 s after closing") instead of a closed/overloaded/open burst. Update the T-8.6 golden event timeline, and record old → new lines in Decisions.

Design (decided; don't re-litigate):
1. **Idle = shadowed and ok.** At the start of each tick, the "gated" edges are the breaker edges admitting less than 100% this tick (open or half-open, i.e. `begun.pass < 1`). A node is *shadowed* when it has at least one forward inbound edge and every forward inbound edge is either gated or comes from a shadowed node. Walk the nodes in topological order. Shadowing is transitive: in App → Payments (breaker) → DB, DB goes idle too. A node with any ungated caller is not shadowed. The state the log reports is `shown = out.state === "ok" && shadowed ? "idle" : out.state`. A line is logged when `shown` differs from what the log last said (the `logged` map replaces `prevState`).
   - idle → ok logs "X recovered".
   - idle → hot logs "X running hot". That is real traffic, which is fine.
   - During the half-open probe tick the node still reads idle.
2. **Re-open collapse = hold, then flush or drop.** When a breaker closes, its "closed — traffic restored" line is held, not emitted. While the hold exists, node lines for nodes *behind* that breaker are held too. A node is behind a breaker when it is shadowed with only that edge gated; this set is computed once per run.
   - **Re-open within the window:** if the breaker trips again (`endBreakerTick` → `"open"`), the held lines are dropped. Each held node's `logged` value goes back to what it was before the hold. Instead of the usual "open at N%" line, one `"{S} → {T} breaker re-opened {gap} s after closing"` line is logged, with gap = (tick − closeTick)/10.
   - **Re-open no longer possible:** the held lines are flushed in order as soon as a re-open can't land within `REOPEN_WINDOW_SEC = 1` of the close. That is the case when the ticks left in the window are fewer than `tripTicks − streak`. Held lines are also flushed on the run's last tick.
   - **Delay:** with the default 0.5 s trip window a genuine close therefore logs 0.6 s late. With a trip window over 1 s it logs on its own tick.
   - Frames are streamed, so lines can't be retracted after they are sent. Delaying the closed line is the only way to meet "one line instead of a closed/overloaded/open burst". **The lead should review this call.**
3. **Event order within a tick.** Half-open lines are emitted at the start of the tick, before node lines, because the probe happens before the nodes run. Then node lines (`graph.nodes` order). Then end-of-tick breaker lines (`graph.edges` order). Today all breaker lines come after the node lines.
4. **Severity.** "X idle (breaker open)" is `info`. This check must come first, because the line contains "breaker open", which currently matches `warning`. "breaker re-opened" is `warning`.

   ```ts
   /** A breaker that re-trips within this long of closing logs one "re-opened" line instead of closed → … → open (T-12.2). */
   export const REOPEN_WINDOW_SEC = 1;

   /** Could a closed breaker still trip within the next `ticksLeft` ticks? (needs tripTicks − streak more ticks over threshold) */
   export function canReopenWithin(
     state: BreakerState,
     cfg: ResolvedBreaker,
     ticksLeft: number,
   ): boolean {
     return state.phase === "closed" && ticksLeft >= cfg.tripTicks - state.streak;
   }

   /** The one line for a breaker that re-opened `afterSec` after closing: "App → DB breaker re-opened 0.5 s after closing". */
   export function breakerReopenedEvent(
     sourceLabel: string,
     targetLabel: string,
     afterSec: number,
   ): string {
     return `${sourceLabel} → ${targetLabel} breaker re-opened ${Math.round(afterSec * 10) / 10} s after closing`;
   }
   ```
