# T-13.1 — Board data: types, persistence, store

## Goal

Give the three Practice step boards (Requirements, Entities, API) a plain-data home. That means types in `core`, a forgiving guard plus defaults in persistence, `DesignRecord.boards` saved, exported and imported (record files and run bundles), and granular design-store actions that T-13.3–T-13.5 call. Board edits autosave like notes and record one debounced `board_edited` action per burst. This task adds no UI.

**Accept (verbatim):**
- Plain-data types for the three boards:
  - Requirements: two ordered lists of `{ id, text, source?: "scenario" }`.
  - Entities: boxes `{ id, name, fields: { id, name, type }[], position: { x, y } }` plus relations `{ id, from, to, kind: "one-to-one" | "one-to-many" | "many-to-one" | "many-to-many" }`.
  - API: endpoints `{ id, method: "GET" | "POST" | "PUT" | "PATCH" | "DELETE", url, status, requestBody, responseBody }`, with the bodies as raw strings.
- The planner names the record field (for example `DesignRecord.boards`).
- `DesignRecord` carries the boards. `parseDesignRecord` is forgiving: a missing field or a malformed field or item yields an empty board, or drops that item. Relations whose `from`/`to` don't name an existing entity are dropped on load.
- The `RunBundle` round-trip keeps boards byte-identical. The planner decides whether `version` stays 1 (forgiving defaults) and logs it.
- design-store exposes the boards plus granular update actions that the three board tasks need. Autosave picks up board changes like notes. Attach and import load them. Board edits record a debounced action-log entry (one per burst, like `note_edited`), so the review timeline shows when artifacts changed. The planner picks the reused or new `ActionKind` and logs it.
- Tests: round-trip a record with all three boards; parse an old record with no boards; parse malformed boards; drop dangling relations; bundle export → parse is identical (review focus 5).

Engine rules: `core` is types only (it exports no values today; keep it that way). The `actions` engine may import `core` types. All values (constants, defaults, the guard) live in the shell (`src/persistence/boards.ts`). Nothing in `src/lib/**` imports react/next/zustand/@xyflow. No new deps.

Calls made (lead, please review):
1. **Record field: `DesignRecord.boards: DesignBoards`**, which is `{ requirements, entities, api }`. The keys equal the `Phase` names (`BoardPhase`), so T-13.2's step switch maps a phase straight to its board.
2. **`RunBundle.version` stays 1.** `boards` is additive and `parseDesignRecord` fills `emptyBoards()` when it's missing, so old bundles load unchanged. Older app builds would just ignore the field.
3. **New `ActionKind` `"board_edited"`**, detail `"edited requirements" | "edited entities" | "edited API"`, with timeline label `"board"`. The store debounces it per board (1000 ms, the same as notes), so editing two boards in one burst gives two entries. The debounce lives in the store, not in the components, so the three board tasks get it for free. Not recorded: `moveEntity` (a box drag, like canvas drags, which record nothing) and the seeding hook (not a candidate edit). Pending timers are cancelled on attach/import.
4. **"Seed once" is persisted:** `RequirementsBoard.nonFunctionalSeeded: boolean`. The flag is set the first time `seedNonFunctional` runs on an attached design, whether or not it added items. If the user deletes every NFR item and reloads, they don't come back. Old designs have no flag, so they get seeded on first open (spec). T-13.3 owns *when* to call the hook and the item texts. T-13.1 owns the "once".
5. **`status: string`** (default `"200"`), raw text as typed, like the bodies (lead call: a half-typed or empty status is never coerced, and T-13.5 needs no draft state). The guard keeps any string as is.
6. **Relations:** the store rejects a second relation between the same two entities (either direction), like the canvas's duplicate-edge no-op. Self-relations (`from === to`) are allowed by the store and the guard, so T-13.4 can still block them in the UI. `repointRelation` is included because it costs about 10 lines.
7. **Kind direction:** a `RelationKind` reads `from → to`. `"one-to-many"` means one `from` to many `to` (the crow's foot sits at the `to` end).
8. **Byte-identical round-trip** relies on the guard rebuilding every object in a fixed key order, and the store's factories using that same order (documented in both files). Duplicate ids inside a collection are dropped on load (later ones lose) so React keys stay unique.
9. Unknown extra keys on board items are dropped on load. A requirement `source` other than `"scenario"` drops the key and keeps the item. An entity whose `fields` isn't an array keeps the entity with `fields: []`, so its relations survive.

Files deviation from the task list: new `src/persistence/boards.ts` (constants, `emptyBoards`, `parseDesignBoards`), because core stays value-free. New `src/stores/board-actions.ts` (the action factory, so design-store stays readable). `src/lib/actions/recorder.ts` (`boardEditedAction`), `src/components/review/timeline.ts` (label), `src/stores/design-file-store.ts` and `ReviewScreen.tsx` (pass `boards` into `buildDesignRecord`, so export doesn't drop them), `01-architecture.md` layout, and the M13 Decisions.

   The guard has one rule set. Every object is rebuilt in the exact key order of the types in step 1, which is the order that keeps the round-trip byte-identical. Put a comment on it saying so.
   - `parseDesignBoards`: if `value` isn't a record, return `emptyBoards()`. Otherwise `{ requirements: parseRequirements(v.requirements), entities: parseEntities(v.entities), api: parseApi(v.api) }`.
   - Requirements: if not a record, use the empty board. Otherwise use one `seen` set for both lists. An item needs a string `id` and `text`. Return `raw.source === "scenario" ? { id, text, source: "scenario" } : { id, text }`. `nonFunctionalSeeded: v.nonFunctionalSeeded === true`.
   - Entities: if not a record, return `{ entities: [], relations: [] }`. A field needs string `id`, `name` and `type`, with ids unique per entity (a fresh `seen`). An entity needs a string `id` and `name` and a record `position` with finite `x` and `y`. It is rebuilt as `{ id, name, fields: parseList(raw.fields, parseField), position: { x, y } }`. A relation needs string `id`, `from` and `to`, and `kind` in `RELATION_KINDS`. After parsing, keep only relations whose `from` and `to` are both ids of the parsed entities. This drops dangling relations, including ones that pointed at an entity dropped as malformed.
   - API: if not a record, return `{ endpoints: [] }`. An endpoint needs a string `id`, `method` in `HTTP_METHODS`, a string `url`, a string `status`, and string `requestBody` and `responseBody`. Otherwise it is dropped. It is rebuilt as `{ id, method, url, status, requestBody, responseBody }`.

   Private pure helpers. Each returns `null` for "no change", and the action then returns without committing or recording:
   ```ts
   function insertAfter<T extends { id: string }>(list: readonly T[], item: T, afterId?: string | null): T[]   // afterId null/undefined/unknown → append
   function moveById<T extends { id: string }>(list: readonly T[], id: string, toIndex: number): T[] | null  // to = clamp(trunc(toIndex), 0, len-1); null if id unknown or to === from
   function patchById<T extends { id: string }>(list: readonly T[], id: string, patch: Partial<T>): T[] | null // apply only keys !== "id" whose value !== undefined and differs; null if none or id unknown
   function removeById<T extends { id: string }>(list: readonly T[], id: string): T[] | null                  // null if id unknown
   ```
   `patchById` must assign onto `{ ...cur }` key by key, as in the snippet below, so it keeps the existing key order and never writes `undefined` (that would drop the key in JSON and the item on the next load). This was type-checked under `--strict`:
   ```ts
   const changed = (Object.keys(patch) as (keyof T)[]).filter((k) => k !== "id" && patch[k] !== undefined && patch[k] !== cur[k]);
   if (changed.length === 0) return null;
   const merged = { ...cur };
   for (const k of changed) merged[k] = patch[k] as T[keyof T];
   ```
   Inside the factory:
   `const commit = <K extends BoardPhase>(key: K, next: DesignBoards[K], record = true) => { setBoards({ ...getBoards(), [key]: next }); if (record) onEdit(key); };`
   Ids come from `crypto.randomUUID()`. Literal key order: requirement `{ id, text }` / `{ id, text, source: "scenario" }`; field `{ id, name, type }`; entity `{ id, name, fields, position: { x, y } }`, where position is always rebuilt from `.x`/`.y`; relation `{ id, from, to, kind }`; endpoint `{ id, method, url, status, requestBody, responseBody }`. Action semantics:
   - `addRequirement(list, afterId, text = "")` inserts `{ id, text }` with `insertAfter` and returns the id.
   - `updateRequirement` uses `patchById(…, { text })` and keeps `source`. `removeRequirement` and `moveRequirement` use their helpers.
   - `seedNonFunctional(texts)`:
     - If `!isAttached()` or `nonFunctionalSeeded`, return `false`.
     - If `nonFunctional` is empty, set it to `texts.map((text) => ({ id: uuid, text, source: "scenario" }))`.
     - Always set `nonFunctionalSeeded: true`, then `commit("requirements", next, false)`, so the change is autosaved but not recorded.
     - Return `true` only if items were added.
   - `addEntity(position, name = "")` appends `{ id, name, fields: [], position }` and returns the id. `renameEntity` uses `patchById(…, { name })`.
   - `moveEntity` sets `position: { x, y }` on the matching entity (no-op if unknown or unchanged) and commits with `record = false`.
   - `removeEntity(id)` removes the entity **and every relation with `from === id || to === id`** in one commit.
   - Field actions find the entity by id (no-op, or `null` from `addField`, if unknown), then apply the list helper to `entity.fields` and commit the entities board with that entity replaced. `addField` creates `{ id, name: init?.name ?? "", type: init?.type ?? "" }` via `insertAfter` and returns the id.
   - `addRelation(from, to, kind = DEFAULT_RELATION_KIND)` returns `null` when either id isn't an entity, or when a relation already joins `{from, to}` in either direction. Otherwise it appends and returns the id. Self-relations are allowed.
   - `setRelationKind` uses `patchById(…, { kind })`.
   - `repointRelation(id, end, entityId)` is a no-op if the relation or the entity is unknown, if nothing changes, or if the new pair duplicates another relation (excluding this one, either direction). Otherwise it patches `{ [end]: entityId }`.
   - `removeRelation` uses `removeById`.
   - `addEndpoint(at = "end", init)` builds `{ id, method: init?.method ?? "GET", url: init?.url ?? "", status: init?.status ?? DEFAULT_ENDPOINT_STATUS, requestBody: init?.requestBody ?? "", responseBody: init?.responseBody ?? "" }`, prepends it for `"start"` and appends it for `"end"`, and returns the id.
   - `updateEndpoint` uses `patchById`. `removeEndpoint` and `moveEndpoint` use their helpers.
   - Every other action commits with recording.
